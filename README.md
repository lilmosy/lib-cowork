# LibCowork

도서관에서 새 책에 **청구기호(852 ▼h)** 를 매기는 일을 돕는 사서-AI 협업 에이전트입니다.

**확실한 책은 답 하나로 끝내고, 판단이 갈리는 책은 후보와 근거를 붙여 사서에게 넘깁니다.**

## 왜 만드나

새 책이 들어오면 사서가 청구기호를 매깁니다. 이 번호가 곧 책이 꽂힐 자리입니다. 이 일에는 성격이 다른 두 문제가 섞여 있습니다.

**① 반복적이다.** 매 권마다 같은 검색을 손으로 되풀이합니다. 업체 번호(082)를 본교에서 확인하고, 타대학 분포를 보고, 다시 본교 서가와 맞춰 봅니다. → **자동화합니다.**

**② 사람마다 갈린다.** 판단이 사서의 암묵지에 기대 있습니다. 사서가 실제로 처리한 책 중에서도 **작성자가 매긴 번호를 교열 담당자가 뒤집은 경우가 여럿 있었습니다.**

| 책 | 작성자 | 교열 최종 |
|---|---|---|
| 사랑받는 서점을 만들기 위해 2000일 | 658.827 (소매경영) | **381.45002** (서적판매업) |
| 어느 완벽한 이중언어자 | 400.42 (언어학) | **306.446** (사회학) |
| 부린 왕자 | 179.9 (자기계발) | **332.6324** (부동산투자) |
| 일리아스 좋아하세요? | 883 (그리스문학) | **028.9** (독서) |

둘 다 틀리지 않았습니다. 같은 책을 어느 관점에서 보느냐의 문제입니다. 그래서 이 도구는 정답을 맞히는 기계가 아니라, **갈리는 지점에서만 사람이 판단하게 만드는 도구**를 목표로 합니다.

## 어떻게 동작하나

사서가 실제로 하는 순서를 그대로 옮겼습니다. LLM 호출은 두 종류뿐이고 나머지는 전부 코드입니다.

- **LLM-F (서가 적합도):** 책 1권과 후보 서가 1곳(본교 장서 40권)을 보고 "이 서가에 꽂혀도 어울리나"를 0~1로 매깁니다.
- **LLM-K (검색어 추출):** 책 정보만 보고 검색어 3~5개를 뽑습니다.

```
책 입력 → 알라딘 보강(책소개·원제)
   ▼
0차  기존 판본·원서 승계    본교에 같은 책의 이전 판이 있으면 그 번호 그대로. LLM 안 부름
   ▼
1단계  082 (업체 번호)       그 번호대 서가에 대해 LLM-F 1회
   ▼
2단계  + 종합서지            타대학 득표 상위 3개 번호를 추가 → 새 후보에만 LLM-F
   ├─ 여기까지로 수렴이면 종결 (키워드 단계를 건너뜀)
   ▼
3단계  + 키워드              LLM-K로 검색어 → 본교 장서에서 2개 이상 걸린 서가 → 새 후보에만 LLM-F
   ▼
판정 (코드)                 1위 점수 ≥ 0.80 그리고 1·2위 격차 ≥ 0.15 → ✅ 수렴
                            아니면 → ⚠️ 사서가 후보와 근거를 보고 고른다
```

설계의 핵심은 세 가지입니다.

- **점수는 후보마다 따로 매깁니다.** 다른 후보, 출처, 득표수, 문턱은 LLM에 보여 주지 않습니다. 그래야 점수가 `(책, 서가)` 하나의 함수가 되고, 같은 눈금으로 문턱을 정할 수 있습니다.
- **판정은 코드가 합니다.** 점수 문턱은 "어떤 서가도 확신하지 못하는 책"을, 격차 문턱은 "그럴듯한 1위 뒤에 경합이 숨은 책"을 걸러 냅니다. 사람이 갈렸던 책은 두 서가가 모두 높은 점수를 받기 때문에, 1위 점수만으로는 잡을 수 없습니다.
- **확정은 항상 사서가 합니다.** 수렴한 책은 기본값이 채워진 확정 버튼을 한 번 누르고, 갈린 책은 후보 중에서 골라야 확정됩니다. 결과는 기록 파일에만 남기고 장서 DB에는 쓰지 않습니다.

각 결정의 근거와 실측은 **[docs/design.md](docs/design.md)** 에 있습니다.

## 결과

임의로 고른 표본 도서로 실험했습니다. 사서가 실제로 처리한 기록을 정답으로 썼습니다.

- **서가 적합도 프롬프트 비교:** 다섯 가지 프롬프트를 3회씩 돌린 결과, 주제·관점과 자료 성격·용도를 따로 매겨 평균하는 `two_axis` 방식이 작성자와 교열이 일치한 책에서 교열 최종 서가를 1위로 둔 비율이 약 92%로 가장 높았습니다. 지금 운영 프롬프트입니다.
- **판정 문턱:** 같은 회차를 다시 읽어 문턱(0.80, 0.15)을 정했습니다. 2단계에서 종결된 책은 반복 실행에서 모두 교열 정답이었고, 사람이 갈렸던 책은 모두 사서에게 넘어갔습니다. 잘못 종결된 경우는 없었습니다.

⚠️ 같은 표본에 다시 적용해 얻은 값이라 **잠정**입니다. 새 책으로 다시 확인할 예정입니다.

## 저장소 구성

```text
lib-cowork/
├── README.md
├── docs/design.md     설계 문서 — 왜 이렇게 만들었는가
├── real/              실제 구현: 파이프라인, 사서용 화면(Streamlit), 실행 CLI
└── experiment/        비교 실험: 표본 도서(골든셋), 프롬프트 5종, 평가 스크립트, 결과
```

## 실행

```bash
cd real
pip install -r requirements.txt
cp .env.example .env        # OPENAI_API_KEY 등
python run.py mybook.json   # 책 한 권 분류
streamlit run app.py        # 사서용 화면
```

본교 장서 DB(1.3GB)와 종합서지 데이터는 저장소에 없으며, **데이터는 요청 시 제공합니다.** 데이터 배치와 설정값은 [real/README.md](real/README.md), 실험 재현은 [experiment/README.md](experiment/README.md)에 있습니다.
